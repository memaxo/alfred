# AI SDK v6 drift fixes + MCP client integration

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan must be maintained in accordance with `.agent/PLANS.md`.

This change targets ALFRED itself (the monorepo runtime + web UI), not applications generated by ALFRED.

## Purpose / Big Picture

After this change, ALFRED’s web chat will correctly reflect AI SDK v6 tool approval semantics (show approval UI only when AI SDK says approval is required; send the correct approval response back to the server), rather than rendering speculative approve/deny buttons that do not correspond to real v6 state.

Additionally, ALFRED will gain first-class “outbound MCP” integration: a user can configure multiple MCP servers (heterogeneous transports and auth), ALFRED will discover tools from those servers, and the assistant/orchestrator will be able to call those tools alongside ALFRED’s native tools. A user will be able to see it working by adding an MCP server, starting a chat, and watching an MCP-prefixed tool call execute successfully (with safe defaults and policy/approval protection).

## Surprises & Discoveries

- Observation: ALFRED currently renders “Approve/Deny” controls opportunistically for any `tool-call` part, without verifying whether the tool actually requires approval or whether AI SDK v6 is in the `approval-requested` state.
  Evidence: `apps/web/src/components/chat-render.tsx` contains speculative commentary and renders `ToolActions` unconditionally when no tool result exists.

- Observation: ALFRED’s web hook returns `addToolResult(...)` that hardcodes `tool: "unknown"`, which is not a stable identifier and prevents precise tool/UI mapping.
  Evidence: `apps/web/src/hooks/use-assistant-stream.ts` calls `chat.addToolResult({ tool: "unknown", toolCallId, output })`.

- Observation: ALFRED already supports “inbound MCP” OAuth (ALFRED as an OAuth provider for MCP clients), but does not currently implement “outbound MCP” (ALFRED connecting to external MCP servers and importing their tools).
  Evidence: `docs/guides/mcp-integration.md` and `packages/auth/src/index.ts` document and implement OIDC Provider + scopes for MCP clients, but no `@ai-sdk/mcp` usage exists in `packages/*`.

- Discovery: Not all AI SDK error classes expose `static isInstance` (e.g. `AI_NoSpeechGeneratedError` in `ai`), so classifier logic must fall back to `error.name` for some v6 errors.
  Evidence: `node_modules/ai/dist/index.mjs` defines `NoSpeechGeneratedError` without an `isInstance` helper.

- Discovery: When resuming an in-progress assistant message (e.g. after tool approval), `readUIMessageStream` must be seeded with the prior `message` so tool output deltas can apply to the existing tool invocation skeleton.
  Evidence: `apps/web/src/lib/api/__tests__/stream-handler.approval.integration.test.ts` uses `readUIMessageStream({ stream, message: approvedAssistant })` to deterministically observe the `output-available` transition.

## Decision Log

- Decision: Fix tool approval UX by aligning with AI SDK v6’s tool approval surface (approval-requested state + explicit approval response API), rather than inventing ALFRED-specific approval UI semantics.
  Rationale: The current UI is misleading and cannot be correct without access to the actual approval state that AI SDK v6 exposes; aligning to v6 reduces drift and makes upstream updates safer.
  Date/Author: 2026-01-10 / assistant

- Decision: Implement outbound MCP integration as an additive tool-source that merges MCP-provided tools into ALFRED’s existing tool catalog at request time.
  Rationale: This preserves ALFRED’s existing tool policy/security model while enabling heterogeneous MCP servers. It also avoids import-time network connections and keeps streaming endpoints stable.
  Date/Author: 2026-01-10 / assistant

- Decision: Map `AI_InvalidToolInputError` to HTTP `422` (unprocessable entity) and stable code `ai_invalid_tool_input`.
  Rationale: Tool input failures are structurally valid requests whose tool payload fails schema validation; `422` communicates “well-formed but semantically invalid” better than a generic `400`.
  Date/Author: 2026-01-10 / assistant

- Decision: Map `AI_UnsupportedFunctionalityError` to HTTP `501` (not implemented) and stable code `ai_unsupported`.
  Rationale: When the selected model/provider cannot support a requested feature, `501` communicates a capability gap without implying user input is malformed.
  Date/Author: 2026-01-10 / assistant

- Decision: Store outbound MCP bearer tokens as environment variable references (not raw token strings) and default imported MCP tools to `needsApproval: true`.
  Rationale: This keeps secrets out of the database and ensures external tool execution is gated by explicit user approval by default.
  Date/Author: 2026-01-10 / assistant

- Decision: Defer outbound MCP OAuth client support (HTTP/SSE + bearer auth only in this implementation).
  Rationale: A correct OAuth client provider requires token storage/refresh semantics and careful UX/security review; bearer/env provides a safe minimal path that unblocks MCP tool import.
  Date/Author: 2026-01-10 / assistant

- Decision: Enable AI SDK `experimental_telemetry` only when `AI_TELEMETRY=1`, and default `recordInputs=false` / `recordOutputs=false` for privacy.
  Rationale: OpenTelemetry exports are valuable for ops, but ALFRED’s prompts and outputs may contain sensitive personal data.
  Date/Author: 2026-01-10 / assistant

## Context and Orientation

ALFRED’s web chat streams AI SDK v6 UI messages over HTTP endpoints implemented as TanStack Start server handlers. The central server handler is:

- `apps/web/src/lib/api/stream-handler.ts`: Validates incoming `UIMessage[]`, builds history context, calls `streamText`, and returns `result.toUIMessageStreamResponse(...)`.

ALFRED defines agents and native tool catalogs in:

- `packages/agent/src/agents.ts`: `ToolLoopAgent` construction and defaults.
- `packages/agent/src/v6.ts`: Wraps “legacy” ALFRED tool definitions into AI SDK v6 `tool(...)` objects.

ALFRED’s current UI message schema and part type guards are:

- `packages/type/src/stream.zod.ts`: Zod schema used by the web API handler for `UIMessage` validation.
- `packages/ui/src/chat/parts.ts`: Type guards and notes about ALFRED’s custom literal `tool-call` / `tool-result` parts vs AI SDK’s template-literal `tool-${toolName}` tool invocation parts.

The web UI chat integration uses:

- `apps/web/src/hooks/use-assistant-stream.ts`: `useChat` + `DefaultChatTransport` wrapper and derived “actions” UI.
- `apps/web/src/components/chat-render.tsx`: Renders parts and currently guesses at approval UI state.

Terminology (plain language):

- “Tool invocation”: The model asked to call a tool. In AI SDK v6, this is represented as a tool-specific UI part that includes both a `state` (e.g., approval requested, running, output available) and `input`/`output`.
- “Tool approval”: A safety mechanism where a tool does not execute automatically until the user explicitly approves it. In AI SDK v6, tools opt into approval by setting `needsApproval`, and the UI must send an explicit approval response back to the server.
- “Outbound MCP”: ALFRED (as a client) connects to external MCP servers and imports their tools/resources/prompts into ALFRED’s tool catalog.
- “Inbound MCP”: External MCP clients connect to ALFRED (as a server) using OAuth scopes. This already exists in ALFRED and is documented in `docs/guides/mcp-integration.md`.

## Plan of Work

### Milestone 0: AI SDK v6 error handling spec (explicit, per-error)

Goal: For every AI SDK error type listed below, ALFRED must have an explicit, intentional handling path (classification, logging, and user-safe surface) in each of the three “front doors” that touch AI SDK:

- The web streaming HTTP endpoints (`apps/web/src/lib/api/stream-handler.ts`)
- tRPC routers that call `generateText/generateObject` (`packages/api/src/routers/*` via `toTRPCError`)
- the workflow runtime streaming adapter (`packages/runtime/src/adapters/ai.ts`)

This milestone is intentionally “spec-first” because ALFRED currently treats most AI failures as generic 500s, which hides actionable distinctions (misconfiguration vs bad input vs transient provider failure vs approval flow errors).

Definitions:

- “Purposeful handling” means: we can point to a branch in code that matches the error type, and that branch decides (a) whether the caller should retry, (b) what safe error code/string to return to the client, and (c) what structured fields to log. No AI SDK error should be silently coerced into a generic “unknown error” unless it is truly unknown.
- “AI SDK error type” means errors whose `error.name` begins with `AI_`, and/or errors that can be detected with the `*.isInstance(error)` helpers exported by the `ai` package for that error class (ALFRED already vendors the AI SDK v6 error reference pages under `docs/reference/ai-sdk-v6/`).

Work:

1. Add a shared error classifier utility that accepts `unknown` and returns a stable classification object used by all three front doors.

   Suggested shape (the exact naming may vary, but keep it a pure function with no side effects):

     classifyAiSdkError(error: unknown) -> {
       name: string | null,              // e.g. "AI_APICallError"
       kind: "client" | "transient" | "misconfig" | "approval" | "tool" | "output" | "unknown",
       retryable: boolean,
       httpStatus: number,               // for HTTP streaming endpoints
       trpcCode: "BAD_REQUEST" | "PRECONDITION_FAILED" | "INTERNAL_SERVER_ERROR" | "TIMEOUT" | ...,
       safeCode: string,                 // stable, non-leaky error code for clients
       safeMessage: string,              // stable, non-leaky short message
       log: Record<string, unknown>,     // structured log fields; may include provider status codes, etc.
     }

   Implementation notes:
   - Prefer `XxxError.isInstance(error)` checks where available; fall back to `error.name === "AI_..."` only when needed.
   - Never include raw provider response bodies or secrets in `safeMessage`.
   - This classifier should be used (not duplicated) from the stream handler, `toTRPCError`, and runtime adapter.

2. Update `apps/web/src/lib/api/stream-handler.ts` to use the classifier in the outermost catch.

   Required behavior:
   - Invalid JSON request body remains `400 invalid_json`.
   - AI SDK “client” errors (invalid argument/prompt/message conversion/tool input/etc.) return `400` with a stable `error` code (e.g. `ai_invalid_request`) and no stack traces.
   - AI SDK “transient” errors (API call failures, download failure, empty response, retry exhaustion) return `502/503` with a stable `error` code (e.g. `ai_upstream_failed` or `ai_retry_exhausted`).
   - AI SDK “misconfig” errors (missing API key, missing setting, no such model/provider/tool) return `500` with a stable `error` code indicating server misconfiguration.
   - AI SDK approval errors return `409` (conflict) or `400` (bad request) based on the classifier decision, with a stable `error` code indicating an invalid approval state.

   Also require that this branch logs structured details for diagnostics (without leaking secrets).

3. Update `packages/api/src/utils/error.ts` (`toTRPCError`) to map classified AI SDK errors into appropriate `TRPCError` codes and messages.

   Constraints:
   - Preserve existing special cases like `biometric_required`.
   - Do not leak raw underlying error strings to the client for provider failures; prefer stable `message` values like `ai_upstream_failed` and include the original error only in `cause`.

4. Update `packages/runtime/src/adapters/ai.ts` to handle classified AI SDK errors.

   Required behavior:
   - Before rethrowing, emit a terminal `WorkflowEvent` that carries the safe code/message, so the UI can render a stable error state for workflow runs (not a generic “runtime_ai_sdk_error”).
   - Log structured details from the classifier.
   - Ensure this does not break abort semantics: abort should still surface as abort, not as an “AI SDK error”.

5. Add tests that prove each AI SDK error class is handled intentionally.

   Tests must cover at minimum:
   - `apps/web/src/lib/api/__tests__/stream-handler.*.test.ts`: verify HTTP status + JSON body mapping for representative errors in each class.
   - `packages/api/src/utils/error.test.ts` (new): verify `toTRPCError` mapping for each AI SDK error.
   - `packages/runtime/src/adapters/ai.test.ts` (new or extend existing runtime tests): verify error-to-WorkflowEvent mapping for each AI SDK error, plus abort behavior.

   The tests may use lightweight synthetic errors with `name` set to the AI SDK name, but for errors where AI SDK exposes `X.isInstance`, prefer constructing real instances when feasible. The goal is to avoid tests that pass while production matching fails.

Explicit per-error handling list (each must have an explicit branch in the classifier, even if several share the same outcome):

- AI_APICallError: transient upstream failure. Retryable depends on status code; default safe handling is retryable=true, HTTP 502/503, safeCode `ai_api_call_failed`.
- AI_DownloadError: transient upstream failure. Retryable=true, HTTP 502/503, safeCode `ai_download_failed`.
- AI_EmptyResponseBodyError: upstream/proxy failure. Retryable=true, HTTP 502, safeCode `ai_empty_response`.
- AI_InvalidArgumentError: client error / programmer error. Retryable=false, HTTP 400, safeCode `ai_invalid_argument`.
- AI_InvalidDataContent: client input error (bad “data-*” payload shape). Retryable=false, HTTP 400, safeCode `ai_invalid_data_content`.
- AI_InvalidDataContentError: same class as above (treat as client error). Retryable=false, HTTP 400, safeCode `ai_invalid_data_content`.
- AI_InvalidMessageRoleError: client error (bad role). Retryable=false, HTTP 400, safeCode `ai_invalid_message_role`.
- AI_InvalidPromptError: client error (bad prompt shape). Retryable=false, HTTP 400, safeCode `ai_invalid_prompt`.
- AI_InvalidResponseDataError: upstream/provider returned invalid shape. Retryable=true by default, HTTP 502, safeCode `ai_invalid_response_data`.
- AI_InvalidToolApprovalError: approval flow error. Retryable=false, HTTP 409 (conflict), safeCode `ai_invalid_tool_approval`.
- AI_InvalidToolInputError: tool input invalid (model/tool schema mismatch). Retryable=false by default, HTTP 422 or 400; choose one and keep consistent. SafeCode `ai_invalid_tool_input`.
- AI_JSONParseError: upstream/provider returned invalid JSON. Retryable=true, HTTP 502, safeCode `ai_json_parse_failed`.
- AI_LoadAPIKeyError: server misconfiguration. Retryable=false, HTTP 500, safeCode `ai_api_key_missing`.
- AI_LoadSettingError: server misconfiguration. Retryable=false, HTTP 500, safeCode `ai_setting_missing`.
- AI_MessageConversionError: client error (bad UIMessage shape) or programmer error. Retryable=false, HTTP 400, safeCode `ai_message_conversion_failed`.
- AI_NoSpeechGeneratedError: output error (feature not used today in web chat, but must be handled). Retryable=false, HTTP 502, safeCode `ai_no_speech_generated`.
- AI_NoContentGeneratedError: model returned no content. Retryable=true (often transient), HTTP 502, safeCode `ai_no_content_generated`.
- AI_NoImageGeneratedError: output error (not used today in web chat). Retryable=false, HTTP 502, safeCode `ai_no_image_generated`.
- AI_NoTranscriptGeneratedError: output error (voice-related). Retryable=false, HTTP 502, safeCode `ai_no_transcript_generated`.
- AI_NoObjectGeneratedError: structured output failed. Retryable=true by default, HTTP 502, safeCode `ai_no_object_generated`.
- AI_NoOutputSpecifiedError: programmer error (call site bug). Retryable=false, HTTP 500, safeCode `ai_no_output_specified`.
- AI_NoSuchModelError: server misconfiguration or user-selected invalid model id. Retryable=false, HTTP 500 (or 400 if user-provided); decide and document. SafeCode `ai_no_such_model`.
- AI_NoSuchProviderError: server misconfiguration. Retryable=false, HTTP 500, safeCode `ai_no_such_provider`.
- AI_NoSuchToolError: misconfiguration or tool catalog mismatch. Retryable=false, HTTP 500 (or 400 if user-provided); decide and document. SafeCode `ai_no_such_tool`.
- AI_RetryError: transient failure with retry exhaustion. Retryable=false (already exhausted), HTTP 503, safeCode `ai_retry_exhausted`.
- AI_ToolCallNotFoundForApprovalError: approval flow error (stale/unknown approval id). Retryable=false, HTTP 409, safeCode `ai_approval_not_found`.
- AI_ToolCallRepairError: tool-call repair failed. Retryable=true by default, HTTP 502, safeCode `ai_tool_call_repair_failed`.
- AI_TooManyEmbeddingValuesForCallError: client error (payload too large). Retryable=false, HTTP 413, safeCode `ai_too_many_embedding_values`.
- AI_TypeValidationError: client/programmer error (schema mismatch). Retryable=false, HTTP 400, safeCode `ai_type_validation_failed`.
- AI_UnsupportedFunctionalityError: feature not supported by provider/model. Retryable=false, HTTP 501 or 400; decide and document. SafeCode `ai_unsupported`.

Acceptance:

For each error name in the list above, there exists at least one test that:
1) feeds that error into the classifier, and asserts the resulting classification object (kind/retryable/status/safeCode), and
2) proves that the appropriate front door surfaces the classification safely (HTTP status + JSON body; tRPC code/message; workflow error event).

### Milestone 1: Make tool approval rendering reflect real AI SDK v6 state

Goal: the chat UI must show approval controls only when AI SDK v6 indicates the tool invocation is in `approval-requested` state, and it must show “running” vs “output available” based on the tool invocation’s real state.

Work:

1. Extend the `packages/type/src/stream.zod.ts` `uiMessageSchema` to accept AI SDK v6 tool invocation parts in addition to ALFRED’s explicit `tool-call`/`tool-result` parts.

   The schema should accept:
   - tool invocation parts whose `type` is `tool-${string}` (template literal)
   - required fields: `toolCallId` (string), `input` (unknown)
   - optional fields: `output` (unknown), `state` (string), `approval` (object with at least `id` string), and any provider metadata (passthrough)

   This must remain tolerant: the UI part structure is library-owned, so the schema should validate the core identity fields but allow extra properties.

2. Update `packages/ui/src/chat/parts.ts` to add new type guards for AI SDK v6 tool invocation parts:
   - `isToolInvocationPart(part)` returns true when `type` starts with `tool-` and `toolCallId` is present.
   - `getToolInvocationState(part)` returns a normalized state union for UI (`approval-requested`, `input-available`, `running`, `output-available`, `error`, `unknown`) based on the part’s fields.

3. Update `apps/web/src/components/chat-render.tsx` to render tool invocations based on the real tool invocation part shape.

   Specifically:
   - If the part is an AI SDK tool invocation part, render it using its state (no “guessing”).
   - If the part is ALFRED’s `tool-call` / `tool-result` format, keep the existing rendering, but remove speculative approval UI (or clearly gate it behind the presence of v6 approval metadata).

4. Add/extend unit tests for the part type guards and renderer behavior.

   Where to add tests:
   - Prefer co-located tests near the module: `packages/ui/src/chat/parts.test.ts` (new) or `packages/ui/src/chat/__tests__/...` if that pattern exists.
   - Add a web component/unit test for `chat-render.tsx` logic if there is an existing React test harness; otherwise, keep renderer testing at the pure-function level.

Acceptance:

By constructing a fake `UIMessage` containing a tool invocation part with `state: "approval-requested"`, the UI should render approval controls. With `state: "running"`, it should not. With `state: "output-available"` and `output` present, it should show output and no approval controls.

### Milestone 2: Wire the correct AI SDK v6 approval response path (no fake “tool result” approvals)

Goal: Approving or denying a tool request in the UI must send the correct approval response shape expected by AI SDK v6, and must unblock the server-side stream.

Work:

1. Update `apps/web/src/hooks/use-assistant-stream.ts` to expose an approval API aligned to AI SDK v6.

   The hook should expose a function named something like:
   - `addToolApprovalResponse({ approvalId, approved })`
   and it should delegate to the AI SDK chat instance’s approval API (do not invent a custom HTTP endpoint; use AI SDK’s built-in mechanism via `useChat` + transport).

   If the AI SDK `useChat` instance also supports `addToolResult`, keep it, but do not use it to represent approval (approval is not a tool output; it is a gate).

2. Update `apps/web/src/components/chat-render.tsx` so the Approve/Deny buttons call `addToolApprovalResponse` with:
   - the `approval.id` from the tool invocation part (not the `toolCallId`)
   - an `approved` boolean

3. Add an integration test for `apps/web/src/lib/api/stream-handler.ts` that proves the end-to-end approval round trip:

   Test shape (high-level):
   - Create a tool with `needsApproval: true` and a simple `execute` function.
   - Start a stream request and assert that a tool invocation reaches the client with `approval-requested`.
   - Simulate sending an approval response and assert the stream continues and the tool eventually reaches `output-available`.

   This test must be deterministic and avoid network calls. It should run under the existing Bun test harness.

Acceptance:

A tool marked `needsApproval` must not execute until the UI approves it, and must execute after approval. Denial must abort or produce an error state that is observable in the message parts.

### Milestone 3: Outbound MCP client integration (multiple heterogeneous MCP servers)

Goal: Allow the user (single-user in ALFRED) to configure multiple MCP servers and import their tools into ALFRED’s assistant/orchestrator tool catalog.

Constraints:

- Do not create network connections at module import time.
- All secrets and tokens must come from the database or environment variables, never hard-coded.
- Tool execution must remain safe by default: prefer `needsApproval` or ALFRED policy gating for MCP tools, since they may call external systems.

Work:

1. Add dependency wiring for AI SDK v6 MCP.

   Add `@ai-sdk/mcp` to the appropriate workspace dependencies (likely root `package.json` under Bun workspaces), using a version compatible with the existing `ai@^6.0.0-beta.137`.

2. Define storage for outbound MCP server configurations.

   Create a new DB table (Drizzle schema + migration) to store per-user MCP server configs. Suggested minimum fields:
   - `id` (uuid)
   - `userId` (string/uuid, matches auth user id type)
   - `label` (string; used for tool name prefixing and UI display)
   - `transport` (enum: http | sse | streamable-http)
   - `url` (string)
   - `authType` (enum: none | bearer | oauth)
   - `authData` (jsonb; contains headers, token references, etc; never store plaintext secrets unless you explicitly document encryption-at-rest)
   - `enabled` (boolean)
   - timestamps

   Add repos under `packages/db` to list and update these configs.

3. Implement an outbound MCP client manager in `packages/agent/src/mcp/`.

   Responsibilities:
   - Given a `userId`, load enabled MCP server configs.
   - For each config, create an MCP client with the appropriate transport and auth.
   - Fetch tools from each client and namespace them to avoid collisions. For example, prefix tool names with `${label}__${toolName}` and embed original identity in tool metadata.
   - Return a merged `Record<string, Tool>` suitable for passing into `streamText` and/or `ToolLoopAgent` calls.
   - Ensure clients are closed in a `finally` block for request-scoped usage; if you add caching, add explicit TTL + teardown and tests that validate no handle leaks.

4. Expose a minimal API and UI for configuration.

   Server-side:
   - Add a small tRPC router (e.g. `packages/api/src/routers/mcp.ts`) for listing/creating/updating outbound MCP server configs.
   - Enforce that only the signed-in user can modify their MCP configs.

   Web UI:
   - Add a settings pane to create/edit MCP servers (label, url, transport, auth type).
   - For OAuth-auth MCP servers, implement a redirect-based flow that stores tokens for the outbound MCP connection in the DB. (AI SDK v6 MCP supports OAuth flows; the plan implementer should integrate this without leaking secrets to the browser.)

5. Merge MCP tools into the streaming tool catalog.

   In `apps/web/src/lib/api/stream-handler.ts`, after `defaults = getDefaults()` and after `userId` is known, fetch MCP tools and merge them into the tool map passed to `streamText`.

   Ensure that:
   - tool name collisions are impossible (prefixing must be deterministic)
   - MCP tools default to safe execution (prefer approval required or explicit allowlist)

Acceptance:

With one configured MCP server, sending a prompt that triggers a prefixed MCP tool call should result in a successful tool invocation and an output visible in the chat UI. With two MCP servers, tools from both should be discoverable and invokable without naming collisions.

## Validation and Acceptance

Acceptance is met when:

1. A tool that does not require approval never shows Approve/Deny UI, and a tool that requires approval shows it only when the invocation is in `approval-requested`.
2. Clicking Approve/Deny sends the correct approval response and deterministically continues or halts tool execution.
3. A user-configured MCP server’s tools show up as callable tools (namespaced), and at least one MCP tool call can be executed end-to-end in the assistant chat.
4. DevTools and telemetry can be enabled by env flags without impacting production behavior or causing tests to hang.

## Idempotence and Recovery

All changes should be additive and safe to run multiple times:

- DB migrations should be forward-only and idempotent in application.
- MCP connections must be cleaned up (client closed) even on abort/error.
- Feature flags (DevTools/telemetry) must default to off and must not cause import-time work.
