# Tool Ontology Artifacts

Owner: agent + runtime

Scope: This plan targets **ALFRED itself** (the monorepo runtime), not apps generated by ALFRED.

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`.

## Purpose / Big Picture

This plan is intentionally minimal. It adds **one** file-based artifact surface that is consistently valuable and cheap to maintain:

- `/.agent/tools/mcp/STATUS.md`: a human-readable snapshot of MCP integration health for the current user (which servers are configured, which could be contacted, and what tool namespaces are available).

It also adds a tiny “orientation” file so a novice (human or agent) knows what `/.agent/tools/` means:

- `/.agent/tools/README.md`: what this directory is for, what files may appear here, and which existing persistence surfaces already exist (AgentFS tool call audit, filesystem diff, Postgres run artifacts).

What this plan explicitly does **not** do (to avoid bloat):

- No `CATALOG.md` generation. AI SDK already provides tool names + descriptions to models; duplicating that into files creates drift.
- No automatic persistence of every tool result into files. That creates `.agent/tools/` pollution and adds a new “artifact subsystem” to maintain.
- No heuristic metadata inference (conflicts with `.ruler/55-llm-first-classification.md` and will rot).

### Observable outcome (what you can see working)

Run any workflow execution that creates an AgentFS workspace and has a `userId`. After workspace initialization:

- `/.agent/tools/README.md` exists
- `/.agent/tools/mcp/STATUS.md` exists and contains a status table (or a clear “no servers configured” message)

## Surprises & Discoveries

This plan’s main “surprise” is that most of what we wanted is already present, just not surfaced as a readable file:

- Observation: MCP tools are already loaded via `packages/agent/src/mcp.ts` and merged into tool maps in `apps/web/src/lib/api/stream-handler.ts`.
  Implication: We should reuse this loader and add a _status report_ export rather than inventing a new MCP subsystem.

- Observation: Workflow runs already create an AgentFS workspace (`packages/runtime/src/orchestrator/agent.ts` via `WorkspaceFactory.create(...)`) that can write files and record tool calls.
  Implication: If we write a status file, do it where we already have `workspaceEnv` + `userId` (the workflow boundary), not inside individual tools.

- Observation: Tool catalogs and “persist everything” quickly become drift and directory pollution.
  Implication: Start with only `STATUS.md` + `README.md`. Everything else should be justified by an observable debugging win.

## Decision Log

- Decision: De-scope to `STATUS.md` + `README.md` only (no catalog, no auto tool-result artifacts).
  Rationale: The “catalog + persist-everything” approach creates drift, directory pollution, and ongoing maintenance burden without a clear, measurable payoff over existing tool schemas + AgentFS audit + file diffs.
  Date/Author: 2026-01-19

- Decision: Implement MCP status by extending `packages/agent/src/mcp.ts` (additive API), then write `STATUS.md` from a workflow boundary where we already have `workspaceEnv` + `userId`.
  Rationale: Reuses a shipping path, avoids new lifecycle management, and keeps side effects at boundaries.
  Date/Author: 2026-01-19

## Context and Orientation

This ExecPlan targets one narrow behavior: writing two files into an AgentFS workspace.

### What “workspace file” means

Paths like `/.agent/tools/mcp/STATUS.md` refer to the **AgentFS virtual filesystem** (see `packages/agent/src/environment/agentfs.ts` and `docs/guides/agentfs-usage.md`). `AgentFSWorkspace` already has `writeFile(...)` and `readFile(...)`.

### Existing MCP integration

`packages/agent/src/mcp.ts` exports `loadMcpTools(userId, signal?)`, which is already used in production (merged into tool maps in `apps/web/src/lib/api/stream-handler.ts`). We will extend this module additively to also expose a status report.

### Where to write files

We only write files in workflow contexts where we have:

- a workspace handle (`workspaceEnv` returned by `WorkspaceFactory.create(...)`)
- and a userId (needed to load configured MCP servers)

The canonical place that has both today is `packages/runtime/src/orchestrator/agent.ts` inside `runAgent(...)` after `await workspaceEnv.initialize()` succeeds.

## Plan of Work

Implement two additive changes:

1. Extend `packages/agent/src/mcp.ts` to expose a `loadMcpToolsWithStatus(...)` export that returns:
   - `tools` (existing behavior)
   - `servers` status list (new)
   - `close()`

2. Write the two files into the AgentFS workspace:
   - `/.agent/tools/README.md` (static content)
   - `/.agent/tools/mcp/STATUS.md` (generated from the server status list)

This work is intentionally narrow: no catalogs, no tool result artifacts, no new type layer.

## Concrete Steps

### Step 1: Add a status-returning MCP loader

File: `packages/agent/src/mcp.ts`

- Add a new exported type:
  - `export type McpServerStatus = { label: string; connected: boolean; toolCount: number; lastResponseMs?: number; lastError?: string; tools: Array<{ name: string; description: string }> }`
- Add a new exported function:
  - `export async function loadMcpToolsWithStatus(userId: string, signal?: AbortSignal): Promise<{ tools: Record<string, Tool>; servers: McpServerStatus[]; close: () => Promise<void> }>`
- Implement existing `loadMcpTools(...)` by delegating to the new function and returning only `{ tools, close }` (no behavior change for existing call sites).

### Step 2: Add markdown generators + write helpers

File: `packages/agent/src/artifact/mcp.ts` (new)

- `generateMcpStatus(servers: McpServerStatus[]): string`
  - Must produce deterministic markdown:
    - `# MCP Server Status`
    - `## Server Status` table
    - tool list by server (namespaced)
- `writeMcpStatus(workspace: { writeFile: (path: string, content: string) => Promise<void> }, servers: McpServerStatus[]): Promise<void>`
  - Writes to `/.agent/tools/mcp/STATUS.md`

File: `packages/agent/src/artifact/readme.ts` (new)

- `generateToolsReadme(): string`
  - Short explanation of:
    - what `/.agent/tools/` is for
    - what `mcp/STATUS.md` means
    - where else persistence exists today (AgentFS tool call audit; filesystem diff; Postgres run artifacts)
- `writeToolsReadme(workspace: { writeFile: (path: string, content: string) => Promise<void> }): Promise<void>`
  - Writes to `/.agent/tools/README.md`

### Step 3: Wire writes into workflow runtime where workspace + userId exist

File: `packages/runtime/src/orchestrator/agent.ts`

In `runAgent(...)`, after `await workspaceEnv.initialize()` succeeds and once `userId` is known:

- If `isAgentFSWorkspace(workspaceEnv)`:
  - `await writeToolsReadme(workspaceEnv)`
  - If `userId` is present:
    - `const { servers, close } = await loadMcpToolsWithStatus(userId, signal)`
    - `await writeMcpStatus(workspaceEnv, servers)`
    - `await close()`

### Step 4: Add tests

File: `packages/agent/test/mcpstatus.test.ts` (new)

- Unit test `generateMcpStatus` output shape (no network).
- Unit test `writeMcpStatus` by writing into an ephemeral AgentFS and then reading the file back.

File: `packages/agent/test/toolsreadme.test.ts` (new)

- Unit test readme generation and write.

### Manual (end-to-end sanity)

Run any workflow that creates an AgentFS workspace (any orchestrator run that goes through `packages/runtime/src/orchestrator/agent.ts` with AgentFS enabled). Then inspect the workspace:

- `/.agent/tools/README.md` exists and is readable
- `/.agent/tools/mcp/STATUS.md` exists
  - If no MCP servers configured for the user, it should say so explicitly
  - If servers exist, it should show connected/disconnected and tool counts

## Idempotence and Recovery

- `README.md` and `STATUS.md` are overwrite-safe and should be regenerated on each run.
- If MCP load fails, `STATUS.md` should still be written with a clear error summary (do not crash the workflow).

## Interfaces and Dependencies

- **No new shared types in `@alfred/type`**.
- `packages/agent/src/mcp.ts` remains the canonical MCP loader module; we only add `loadMcpToolsWithStatus` and keep `loadMcpTools` stable.
- Artifact outputs are limited to:
  - `/.agent/tools/README.md`
  - `/.agent/tools/mcp/STATUS.md`
