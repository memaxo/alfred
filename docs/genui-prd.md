# Generative UI as First-Class Conversation Output PRD

Owner: product

ALFRED should render responses in their **optimal visual form**, not just text. When Alfred answers a question, executes a task, or reports progress, the output should be the most effective representation for that content—charts for data, timelines for progress, forms for input collection, grids for structured information. This applies across web desktop, mobile, and voice interactions.

## Scope clarity

- **This PRD targets ALFRED itself** (the assistant + its web/native clients + backend), not apps generated by ALFRED for end users.
- **Complements Concierge Focus**: GenUI is the visual layer that makes Focus Board, Attention Queue, Delta Briefs, and workflow progress tangible and interactive.
- **Single-user by design**: optimize for one human's preferences and screen contexts.

## Problem statement

Today, ALFRED's GenUI infrastructure exists but is underutilized:

- **Tools return data, not visuals**: Assistant tools return JSON that renders as code blocks, not as appropriate visualizations.
- **Mobile shows JSON**: React Native renders `data-ui` parts as formatted JSON text, not actual components.
- **No LLM-driven schema selection**: Schemas are hardcoded in workflow handlers; the LLM doesn't dynamically choose representations.
- **Forms don't close the loop**: Form components exist but user input doesn't flow back to the conversation.
- **Voice responses lack visual complement**: Voice outputs produce text; the visual counterpart is an afterthought.

## Vision (what "GenUI as First-Class Output" means)

ALFRED doesn't just answer—it renders the answer in its ideal form:

- **Adaptive representation**: The same data might render as a chart on desktop, a simplified list on mobile, or a spoken summary with a notification card during voice.
- **Progressive streaming**: UI components appear as they're generated, not after the full response completes.
- **Interactive outputs**: Charts filter, timelines expand, forms submit—outputs are not static.
- **Voice + visual synergy**: Spoken responses are complemented by visual artifacts, not duplicated.
- **Cross-platform parity**: The same schema renders appropriately on web, mobile, and TUI.

## Relationship to Concierge Focus

GenUI is the **presentation layer** for Concierge Focus primitives:

| Concierge Concept | GenUI Rendering                                                   |
| ----------------- | ----------------------------------------------------------------- |
| Focus Board       | `grid` of commitment cards with `progress-window` per run         |
| Attention Queue   | `list` of attention items with `confirm` actions                  |
| Delta Brief       | `workflow-timeline` of changes + `chart` of metrics               |
| Running Workflows | `streaming-terminal` + `task-tracker` + live `progress-window`    |
| Voice Call Screen | `plan` summary + `confirm` options + `orb` visualization          |
| Needs Decision    | `confirm` with options + contextual `chart`/`grid` if data-driven |

## Definitions (feature taxonomy)

### Core concepts

- **UIComponent schema**: JSON structure with `component`, `props`, `children`, `key` that describes a renderable component tree.
- **data-ui part**: A message part with `type: "data-ui"` containing a `UIComponent` schema and optional backing `data`.
- **GenUIToolResult**: A tool result that includes both `ui` (the schema) and `data` (the raw data), enabling both visual and programmatic consumption.
- **Component registry**: A runtime map of component names to React component implementations.
- **Schema interpreter**: The recursive renderer that turns `UIComponent` schemas into React nodes.

### Component categories

- **Data visualization**: `chart`, `grid`, `list`, `number`, `matrix`, `term`
- **AI conversation**: `plan`, `task`, `tool`, `think`, `confirm`, `cite`, `branch`
- **Orchestration**: `workflow-timeline`, `progress-window`, `task-tracker`, `streaming-terminal`, `error-panel`, `artifact-browser`
- **Forms**: `text`, `select`, `date`, `daterange`, `checkbox`, `choice`, `autocomplete`
- **Voice/Audio**: `orb`, `wave`, `viz`, `audio`
- **Canvas/Preview**: `preview`, `node`, `artifact`, `panel`, `canvas`

### Rendering contexts

- **Web desktop**: Full component library, rich interactivity, larger viewports
- **Mobile native**: Simplified components, touch-optimized, smaller viewports
- **Voice overlay**: Minimal visual complement to spoken output, notification-style
- **TUI**: Text-based rendering of component semantics (ASCII charts, tables)

## Target user

- A single "power user" who wants ALFRED's outputs to be immediately useful without copy-pasting JSON or mentally parsing raw data.

## Jobs-to-be-done (JTBD)

- **See, don't parse**: "Show me the data in a way I can understand at a glance."
- **Act, don't transcribe**: "Let me make decisions directly in the response, not by typing commands."
- **Track, don't ask**: "Show me live progress without me having to check."
- **Input, don't describe**: "Let me fill out what you need instead of explaining it in text."

## User journeys

### 1) Data query → Adaptive visualization (2-5 seconds)

1. User asks: "How are my tests performing this week?"
2. Alfred analyzes test results and determines: numerical trend data → `chart`; top failures → `list`; summary stat → `number`.
3. Alfred streams response with progressive UI:
   - First: `number` showing 94% pass rate (animated)
   - Then: `chart` showing daily trend
   - Finally: `list` of top 5 failing tests
4. User sees visualization building as Alfred speaks/types the summary.

### 2) Decision needed → Interactive confirmation (3-10 seconds)

1. Workflow blocks: deployment needs approval.
2. Alfred renders:
   - `plan` showing what will be deployed
   - `confirm` with options: "Deploy to preview", "Deploy to production", "Cancel"
   - `chart` showing recent deployment success rate (context)
3. User taps "Deploy to preview" directly in the UI.
4. Alfred resumes workflow with the decision, no typing required.

### 3) Voice request → Visual complement (5-15 seconds)

1. User (voice): "What's the status of the auth refactor?"
2. Alfred (voice): "The auth refactor is 60% complete. Two tasks are blocked waiting for API keys."
3. Alfred (visual, in parallel):
   - `progress-window` showing phase completion
   - `task-tracker` with blocked tasks highlighted
   - `confirm` offering "I'll get the keys" or "Remind me later"
4. User sees the visual while hearing the summary—complementary, not redundant.

### 4) Form collection → Structured input (15-60 seconds)

1. User: "Help me create a new Linear issue"
2. Alfred renders a form:
   - `text` for title
   - `select` for project
   - `select` for priority
   - `autocomplete` for assignee
   - `text` (multiline) for description
3. User fills form, submits.
4. Alfred receives structured input, creates issue, confirms with `task` showing the created issue.

### 5) Background work → Live dashboard (continuous)

1. User starts a focus period with 3 commitments.
2. Alfred renders Focus Board:
   - `grid` of 3 commitment cards (each a `plan` component)
   - Per-commitment: `progress-window` + `workflow-timeline`
   - Attention queue: `list` of items needing input
3. As work progresses:
   - `number` stats animate (tasks completed, time elapsed)
   - `workflow-timeline` updates with new phases
   - `confirm` items appear when decisions needed
4. All updates stream in real-time via subscriptions.

## UX principles

- **Optimal by default**: Alfred chooses the best representation; user can override.
- **Progressive disclosure**: Start with summary, expand to detail on interaction.
- **Streaming-first**: Components appear as they're generated, not after.
- **Touch-friendly**: All interactive elements work on mobile without hover.
- **Accessible**: Components meet WCAG AA; screen reader compatible.
- **Fallback gracefully**: If a component fails, show structured data; never crash.

## Functional requirements (high level)

### LLM schema generation

- LLM must be able to generate `UIComponent` schemas via `generateObject` with structured output.
- Schema selection must consider: data shape, user context, screen size, conversation mode.
- Streaming schema generation via `useObject` for progressive UI.
- Model capability detection before requesting structured output.

### Component rendering

- Registry must be initialized before any GenUI rendering.
- Interpreter must handle unknown components gracefully (placeholder, not crash).
- Error boundaries must wrap all GenUI renders.
- Depth limiting must prevent infinite recursion (default: 10 levels).

### Cross-platform parity

- Mobile registry must include RN-compatible versions of all components.
- Same schema must render appropriately on web and mobile.
- TUI must render semantic equivalents (tables, ASCII charts) for key components.

### Tool integration

- Assistant tools must be able to return `GenUIToolResult` with both `ui` and `data`.
- Helper functions must exist for common patterns: `createChartResult`, `createGridResult`, etc.
- Tools must declare their GenUI capability so the orchestrator can choose appropriately.

### Form submission

- Form components must emit submission events.
- Submitted data must flow back to assistant context as tool results.
- Validation errors must render inline in the form.

### Voice integration

- Voice workflows must produce `data-ui` parts alongside spoken text.
- Visual components must complement, not duplicate, spoken content.
- Notification cards must summarize GenUI for quick glance.

## Non-goals (for this PRD)

- **User-defined components**: Users cannot create custom components; only registered primitives.
- **Arbitrary code execution**: Schemas cannot contain executable code; only declarative props.
- **Cross-user component sharing**: No component marketplace or sharing (single-user system).
- **Perfect mobile parity**: Some components may render simplified on mobile; full parity is aspirational.

## Success metrics (product)

- **Adoption**: >60% of tool results render as GenUI (not JSON) within 3 months.
- **Interaction**: >30% of GenUI renders receive user interaction (click, submit, expand).
- **Mobile parity**: >80% of web components have mobile equivalents within 6 months.
- **Streaming latency**: First GenUI element visible within 500ms of response start (p95).
- **Error rate**: <1% of GenUI renders fail to error boundary.

## Risks & open questions

- **Model capability variance**: Not all models support structured output; fallback strategy needed.
- **Schema complexity**: Deep/complex schemas may be slow to generate; budget constraints needed.
- **Mobile performance**: React Native component rendering must stay under 16ms frame budget.
- **Form security**: Form submissions must be validated; injection attacks possible via schemas.
- **Accessibility**: Generated schemas may not be accessible by default; validation needed.

## PRD appendix — implementation modules & pattern templates

### API (services): schema generation

- **`SchemaGenerator`** (`packages/api/src/services/schema.ts`)
  - **Pattern from**: `packages/api/src/services/compilation.ts` (build artifacts from events).
  - **Purpose**: Generate optimal `UIComponent` schema from tool result data.
  - **Key functions**:
    - `selectComponent(data, context)`: Choose component type from data shape
    - `generateSchema(data, component, context)`: Build full schema with props
    - `streamSchema(data, context)`: Progressive schema generation

- **`FormHandler`** (`packages/api/src/services/form.ts`)
  - **Pattern from**: `packages/api/src/voice/workflow-handler.ts` (handle specialized input).
  - **Purpose**: Route form submissions back to conversation context.
  - **Key functions**:
    - `submitForm(formId, data, conversationId)`: Inject form result as tool result
    - `validateForm(schema, data)`: Validate submission against schema

### API (routers): form submission endpoint

- **`genuiRouter`** (`packages/api/src/routers/genui.ts`)
  - **Pattern from**: `packages/api/src/routers/assistant.ts` (conversation input handling).
  - **Purpose**: Handle form submissions and GenUI interactions.
  - **Endpoints**:
    - `genui.submit`: Submit form data, returns confirmation
    - `genui.interact`: Record interaction (expand, filter, etc.)

### UI (packages/ui): mobile registry

- **`MobileInterpreter`** (`packages/ui/src/genui/mobile.tsx`)
  - **Pattern from**: `packages/ui/src/genui/interpreter.tsx` (schema rendering).
  - **Purpose**: React Native-compatible schema interpreter.
  - **Key differences**:
    - Uses `View`/`Text` instead of `div`/`span`
    - Touch-optimized interaction handlers
    - Simplified component variants

### Native app: GenUI integration

- **`GenUI registry`** (`apps/native/components/genui/registry.ts`)
  - **Pattern from**: `apps/web/src/components/genui/registry.ts`.
  - **Purpose**: Register React Native component implementations.

- **`GenUI renderer`** (`apps/native/components/genui/renderer.tsx`)
  - **Pattern from**: `apps/web/src/components/chat-render.tsx` (`renderGenUI`).
  - **Purpose**: Render `data-ui` parts in message bubbles.

- **Component implementations** (`apps/native/components/genui/components/`)
  - `chart.tsx`: Victory Native or similar
  - `grid.tsx`: FlatList-based grid
  - `list.tsx`: Animated FlatList
  - `number.tsx`: Animated number display
  - `confirm.tsx`: Button group
  - `form/*.tsx`: Form field components

### Agent (tools): GenUI-enabled tools

- **Tool wrappers** (`packages/agent/assistant/src/tool/genui/`)
  - **Pattern from**: `packages/ui/src/genui/tool.ts` (helper functions).
  - **Purpose**: Wrap existing tools to emit GenUI results.
  - **Example**:

    ```typescript
    // Before
    return { success: true, data: results };

    // After
    return createChartResult(
      { type: "bar", data: results.map((r) => ({ x: r.date, y: r.count })) },
      { results }
    );
    ```

### Type (shared contracts)

- **`ComponentCapability`** (`packages/type/src/genui.ts`)
  - **Purpose**: Declare what GenUI a tool can produce.
  - **Shape**:
    ```typescript
    interface ComponentCapability {
      component: string;
      dataShape: ZodSchema;
      contextHints: string[];
    }
    ```

- **`FormSubmission`** (`packages/type/src/genui.ts`)
  - **Purpose**: Form submission payload type.
  - **Shape**:
    ```typescript
    interface FormSubmission {
      formId: string;
      conversationId: string;
      toolCallId?: string;
      data: Record<string, unknown>;
      timestamp: number;
    }
    ```

### TUI: text-based GenUI

- **`TUIInterpreter`** (`packages/tui/src/genui/interpreter.ts`)
  - **Pattern from**: `packages/ui/src/genui/interpreter.tsx`.
  - **Purpose**: Render schemas as text/ASCII.
  - **Mappings**:
    - `chart` → ASCII bar chart
    - `grid` → Table with borders
    - `list` → Bulleted list
    - `number` → Highlighted number
    - `confirm` → Numbered options

## Implementation phases

### Phase 1: LLM schema generation (foundation)

1. Add `generateObject` support for `UIComponent` schema in assistant router
2. Create `SchemaGenerator` service with data shape → component mapping
3. Add model capability detection in `@alfred/cortex`
4. Update voice workflow handler to use schema generator

### Phase 2: Mobile GenUI rendering

1. Create React Native component registry
2. Port core components: `chart`, `grid`, `list`, `number`, `confirm`
3. Update `MessageBubble` to use GenUI renderer
4. Test cross-platform schema rendering

### Phase 3: Tool GenUI integration

1. Create tool wrapper pattern with `createGenUIResult`
2. Upgrade high-value tools: data queries, code analysis, search
3. Add tool capability declarations
4. Update tool result rendering to prefer GenUI

### Phase 4: Form submission flow

1. Create `genuiRouter` with `submit` endpoint
2. Add form submission handler in GenUI components
3. Wire form results back to conversation context
4. Add validation and error rendering

### Phase 5: Polish and optimization

1. Streaming schema generation with `useObject`
2. Component lazy loading for performance
3. Accessibility audit and fixes
4. TUI GenUI rendering
