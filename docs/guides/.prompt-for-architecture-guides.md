# Prompt: Create High-Level Architecture Guides for ALFRED

## Context

ALFRED is a personal AI assistant built as a Better-T-Stack monorepo. It features a sophisticated cognitive architecture with event-sourced state machines, a knowledge hypergraph, voice capabilities, workflow orchestration, and deep integration with Linear. The codebase is well-structured but complex, requiring clear architectural documentation to onboard new developers quickly.

## Task

Create comprehensive, high-level architecture guides in `docs/guides/` that explain ALFRED's core concepts, architectural decisions, and system design. These guides should be written for developers who are new to the codebase but experienced in software engineering.

## Style Guidelines

### Writing Style

- **High-quality prose**: Write in clear, engaging prose that reads like documentation from a mature open-source project (think React, Next.js, or Vercel's documentation style)
- **Paragraph format**: Use flowing paragraphs with clear topic sentences. Avoid bullet-heavy lists except for summaries or quick references
- **Minimal code**: Include code excerpts only when they illustrate architectural concepts. Prefer explanations over code dumps
- **Conceptual focus**: Explain *why* and *how* systems work, not just *what* they do. Focus on architectural patterns, design decisions, and mental models
- **Accessible but deep**: Assume readers are competent developers but new to ALFRED. Explain domain-specific concepts (event sourcing, cognitive state machines, autonomy gradients) clearly

### Structure

Each guide should:

1. **Opening**: Hook the reader with a clear problem statement or compelling overview
2. **Core Concepts**: Explain the fundamental ideas in 2-3 paragraphs
3. **Architecture**: Describe how components fit together (3-5 paragraphs)
4. **Design Decisions**: Explain key choices and trade-offs (2-3 paragraphs)
5. **Integration Points**: Show how this system connects to others (1-2 paragraphs)
6. **Closing**: Summarize key takeaways or point to related documentation

### Tone

- **Confident but humble**: Present architectural decisions as thoughtful choices, not dogma
- **Educational**: Teach concepts, not just document them
- **Inspiring**: Help readers understand the elegance and intentionality of the design
- **Practical**: Connect concepts to real-world benefits and use cases

## Examples of Good Style

### Good Opening (from React docs style):

> ALFRED's cognitive state machine is the beating heart of the assistant. Unlike traditional request-response systems, ALFRED maintains continuous awareness of its own cognitive state—whether it's idle and waiting, deep in thought, making decisions, or reflecting on outcomes. This statefulness enables ALFRED to learn from every interaction, adapt its behavior based on context, and maintain coherence across conversations that span hours or days.

### Good Conceptual Explanation:

> Event sourcing provides more than just an audit trail. By storing every state change as an immutable event, ALFRED can replay any conversation from scratch, debug issues by examining the exact sequence of events that led to a decision, and even experiment with alternative outcomes by replaying events with different parameters. This determinism is crucial for a learning system: if ALFRED can't reliably reproduce its own reasoning, it can't learn from mistakes or improve its decision-making.

### Good Design Decision Explanation:

> The choice to use a hypergraph instead of a simple vector database reflects ALFRED's need to understand not just semantic similarity, but structural relationships. When ALFRED remembers that "deploying to production requires a code review," it's not just storing a fact—it's capturing a relationship between concepts (deployment, production, code review) that can be traversed, queried, and reasoned about. This structural knowledge enables ALFRED to understand dependencies, infer implications, and make connections that pure semantic search would miss.
