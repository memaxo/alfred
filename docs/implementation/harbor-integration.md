# harbor-integration

**Owner:** runtime / infra

## Purpose

Assess feasibility of integrating **Harbor** into **ALFRED** to evaluate and improve ALFRED’s orchestration/execution of many concurrent subagent waves (Codex/Droid/OpenCode), with durable trajectories and metrics suitable for regression tracking and learning loops.

References:
- Harbor core concepts: [Core Concepts](https://harborframework.com/docs/core-concepts)
- Harbor running evals: [Getting Started](https://harborframework.com/docs/getting-started)
- Harbor trajectory schema: [Agent Trajectory Format (ATIF)](https://harborframework.com/docs/trajectory-format)

## Scope clarity (ALFRED vs generated apps)

- **This targets ALFRED itself**, specifically the workflow/orchestrator runtime and evaluation plumbing.
- It does **not** target applications generated by ALFRED.

## What ALFRED already has (strong alignment)

### 1) Multi-agent “wave” runtime with Codex/Droid/OpenCode executors

- The workflow orchestrator runs waves of agents via `runWaves()`:
  - `packages/runtime/src/orchestrator/waves.ts`
- Individual agent execution supports multiple executors:
  - `type AgentExecutor = "codex" | "droid" | "opencode"` in `packages/runtime/src/orchestrator/agent.ts`

### 2) Durable, persisted event stream per run (trajectory-ready)

ALFRED’s `WorkflowEvent` type already includes:
- `tool-call` and `tool-result` (with `toolCallId`, `toolName`, `input`, `output`)
- `ui-message` with `UIMessage[]` parts (including explicit persisted tool parts)
- wave/phase/agent lifecycle markers (`wave-start`, `agent-start`, `agent-complete`, etc.)

See:
- `packages/type/src/plan.ts` (`export type WorkflowEvent = ...`)

Workflow events are persisted with `workflowRepo.appendEvent()` and replayed with `workflowRepo.listEvents()`:
- `packages/db/src/repo/workflow.ts`

**Implication:** ALFRED can emit a Harbor-compatible ATIF trajectory without invasive instrumentation; it is primarily a transformation/export step.

### 3) Eval persistence primitives (overlap with Harbor)

ALFRED already has a DB-backed eval domain:
- definitions, datasets, points, runs, scores: `packages/db/src/repo/eval.ts`
- API router scaffolding: `packages/api/src/routers/eval.ts`
  - `run.start` is currently disabled (`NOT_IMPLEMENTED`, `eval_run_disabled`)

**Implication:** Harbor adds “job/trial” orchestration + standardized ATIF, but ALFRED already has storage primitives for datasets/scores. Integration should avoid duplicating/fragmenting the source of truth.

## Harbor ↔ ALFRED concept mapping

From Harbor:
- **Task**: instruction + container environment + test script
- **Dataset**: collection of tasks
- **Trial**: one agent attempt at a task (produces reward)
- **Job**: many trials (parallel)
([Core Concepts](https://harborframework.com/docs/core-concepts))

Proposed mapping:
- **Harbor Task** ↔ ALFRED “workflow run template”:
  - requirement (prompt/instruction)
  - repository/workspace state (AgentFS overlay + optional seed commit/branch)
  - deterministic verification (test command(s), lint/typecheck gates)
- **Harbor Trial** ↔ one ALFRED workflow run (`workflow_runs.id`) producing:
  - persisted workflow event stream (trajectory)
  - terminal status (completed/failed/suspended/cancelled)
  - metrics (latency, cost/tokens when available, tool stats, wave utilization)
- **Harbor Job** ↔ batch runner over many ALFRED runs:
  - can be Harbor-native (Python driving ALFRED) or ALFRED-native (Bun driving itself) while exporting ATIF for Harbor downstream.

## Integration options (recommended path)

### Option A — “ATIF export only” (recommended first step)

Implement a pure export layer:
- Input: `(runId) → workflow_runs + workflow_events`
- Output: `trajectory.json` in Harbor ATIF v1.x shape, plus summary metrics
- Location: `.agent/plans/<runId>/trajectory.json` (or a parallel `runs/<runId>/trajectory.json`)

Benefits:
- Minimal coupling (no Python runtime embedded into ALFRED)
- Immediate compatibility with Harbor validators/analysis pipelines
- Enables regression tracking + visualization without changing orchestration logic

Risks / gaps:
- Token/cost metrics may be partial depending on which executor emits usage events.
- “Observation” grouping in ATIF may require coalescing `tool-call`+`tool-result` pairs.

### Option B — “Harbor drives ALFRED” via adapter (medium effort)

Harbor runs tasks; the task’s agent is “ALFRED orchestrator”:
- A Harbor adapter launches ALFRED runs (CLI or HTTP API), then runs verification scripts.
- Trials can be horizontally scaled using Harbor’s sandbox support.

Benefits:
- Harbor-native dataset/job orchestration, parallelism, and reward aggregation.
- Natural fit for evaluating “many tasks concurrently” (your stated goal).

Risks:
- Cross-language bridge (Python Harbor ↔ Bun/TS ALFRED).
- Resource oversubscription (Harbor concurrency × ALFRED wave parallelism). Requires careful limits (e.g., set `ORCHESTRATOR_MAX_PARALLEL=1` under Harbor).

### Option C — Deep integration / learning loop (highest effort)

Feed Harbor trial outcomes back into ALFRED’s learning systems:
- Persist successful/failed patterns keyed by project + task type.
- Update planner/decomposer parameters using reward-driven search.

This is plausible, but should follow only after A/B are stable and we have reliable scoring signals.

## What makes this feasible (key evidence)

- ALFRED already produces structured events well-aligned with ATIF’s requirements:
  - tool calls/results are explicit and ID-linked
  - agent/wave lifecycle events exist for stratified metrics (per wave, per agent)
- Harbor’s ATIF is explicitly intended as an interchange format for:
  - “complete interaction history” (messages + tool executions + environment feedback)
  - downstream debugging/visualization/SFT/RL pipelines
([ATIF docs](https://harborframework.com/docs/trajectory-format))

## Recommended next actions

1. **Implement ATIF exporter** for `workflow_runs` / `workflow_events` (Option A).
2. **Add a small regression harness**: select a stable dataset of ALFRED “coding projection” tasks and run N trials nightly/on-demand.
3. **Only then** decide whether Harbor should be the primary runner (Option B) or ALFRED should remain primary runner and Harbor is analysis-only.
